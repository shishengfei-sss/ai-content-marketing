阅读指南：这份文档讲什么？

智营获客的「智能体」不是单独的聊天窗口，而是后端一整套 AI 编排系统：用户在前端（Web 创作页 / H5）说话 → 后端判断意图 → 调知识库、调大模型、生成方案或正文 → 必要时暂停等人确认 → 最后才能发布。

你可以这样读：

  • 产品 / 业务：看 §1 概述、§3 业务流程、§9 Confirm 闸——了解用户从输入到发布的完整路径。
  • 前端开发：看 §4 API、§5 前端调用——直接对照 Create.vue 接入。
  • 后端 / 架构：看 §2 分层图、§6～§8 编排模式 / 多 Agent / 工具表。
会话（Session）
一次连续对话的「文件夹」。用户打开创作页会先创建或恢复 sessionId，后续 chat、消息历史都挂在这个 ID 下。
编排
后端决定「这一步该干什么」：是直接追问、出选题方案、写正文，还是走多步工作流。前端只负责传 message 和展示返回的 action。
Tool（工具）
智能体可以调用的具体能力，如「搜知识库」「生成正文」「查合规」。每个工具在服务端注册，带权限校验。
Workflow（工作流）
把多个工具按固定顺序串起来（如：检索 → 分析 → 出方案 → 写稿 → 合规），适合「一键创作」按钮。
Confirm 闸
发布、排期等「写出去」的操作，AI 只能提议，必须用户在界面上点确认后才真正执行（BR-01）。

1. 概述

FastAPI 后端为唯一权威执行层，Web / H5 统一调用 /api/v1/agent。主线产品为通用营销创作顾问（小营）：公众号 / 小红书 / 抖音选题、写稿、合规与发布准备。

能力域状态说明
会话与消息已落地AgentSession / AgentMessage
意图解析对话已落地默认 chat：LLM JSON → proposals / generate / clarify
ReAct 编排已落地mode=react，最多 8 步 Tool 循环
SSE 流式已落地正文生成 token 流式推送
Workflow + Confirm已落地Pipeline 暂停等人选；发布须 confirm
长期记忆 / 人格库已落地用户/企业事实 + P-001～P-009 变体锁定
AI 销售经理扩展中复用本框架 + CRM 子 Agent（v1.6）
服务端强制原则：权限与额度在 API 校验（BR-01 禁止自动发布）· 合规仅建议/拦截 · Prompt 写原则不写问卷树

一句话：用户跟「小营」聊天写营销内容，所有「能不能发、扣不扣额度、有没有权限」都由后端 API 说了算，前端和 Prompt 不能绕过。

上表各能力域含义：

  • 会话与消息——像微信聊天记录，存在数据库里，刷新页面可以拉历史。
  • 意图解析——用户说「帮我写小红书」，后端先判断是要「出方案」还是「直接写正文」还是「信息不够要追问」。
  • ReAct——更「自主」的模式：大模型自己决定下一步调哪个工具，最多 8 步（实验/高级场景）。
  • SSE 流式——写正文时一个字一个字蹦出来，体验更好（创作页默认用这个）。
  • Workflow + Confirm——一键创作走固定流水线；发布必须用户点确认。
  • 记忆 / 人格库——记住用户偏好（如「语气要亲切」）；对话第 3 轮起锁定一种写作人格。

2. 分层架构图

请求自上而下：客户端 → Router → 编排层 → Tool / 多 Agent → 知识 & Prompt → LLM → 数据库

可以把下图理解成一栋楼的分层：用户只在最顶层（创作页）操作，每一层只做自己的事，下层不知道 UI 长什么样。

  • Web / H5——只负责展示对话、方案卡片、发布确认弹窗；不自己调大模型。
  • API 层——统一入口 /api/v1/agent，校验登录、租户、权限（如有没有 content.create）。
  • 编排层——「大脑」：根据请求类型走 chat、流式、预检或工作流四条路之一。
  • Tool Registry——「手」：真正干活（搜库、生成、合规检查）；按角色分给 Creator / Compliance / Ops 等。
  • 知识与 Prompt——「记忆与话术」：从知识库捞资料、拼系统提示词、注入用户长期记忆和人格。
  • llm_service——统一调大模型；平台额度或租户自己的 API Key。
  • 数据库——会话、消息、工作流状态、待确认发布等全部落库。

3. 核心业务流程

产品里常见三条用户路径，对应下面三个子图。日常创作页以 3.1 标准对话 为主；点「一键创作」走 3.2 Workflow；点「发布」走 3.3 Confirm 闸。

3.1 标准对话（意图解析 + SSE）

用户在创作页输入一句话后的默认路径（Web Create.vue 主流程）。

  1. preflight（可选）——检查输入是否太模糊（如只说「写一篇」），不够就追问，避免浪费额度。
  2. chat / chat/stream——把用户消息发给后端；流式版边生成边显示。
  3. intent_parser——大模型输出结构化结果，决定下一步是 proposals（出方案）、generate（写正文）、clarify（追问）还是 chat（闲聊）。
  4. UI 渲染——前端根据返回的 action 字段展示不同组件（方案列表 / 正文预览 / 追问气泡）。
💡 若 action=clarify，流程在此结束，不会扣正文生成额度。用户补充主题后再发一次 chat。

3.2 Workflow 两段式（propose → resume）

阶段一 content_propose 跑完后 status=paused 等人选；阶段二 resume 追加 content_finish 步骤。合规 block 时 Supervisor 自动改稿再审（最多 N 轮）。

为什么分两段？ 出方案和写正文之间必须让人选一个标题/方向，不能 AI 自作主张。所以第一段跑完会暂停，把方案列表还给前端；用户点选后，前端再调 resume 触发第二段。

  • 阶段一：搜知识库 → 分析受众痛点 → 生成 3～N 个选题方案 → 返回 paused。
  • 用户操作：在 UI 上点击某一个方案（传入 selected_proposal_index，从 0 开始）。
  • 阶段二：按选中方案写正文 → 自检优化 → 合规审查 →（若不通过则自动改稿循环）→ Ops 检查能否发布。
  • 结束：返回 content_id，前端用内容 ID 拉正文展示；此时还未发布。
💡 黄色虚线框：只有合规结果是 block（严重违规）才会进入改稿循环；warn 仅警告，一般继续往下走。

3.3 Confirm 闸（发布 / 排期）

Workflow 或 chat 生成正文后，用户点「发布」时走的最后一条安全链路。

设计原因（BR-01）： 不能让 AI 误触或擅自把内容发到公众号。所以 publish_content 工具不会真的发布，只是在数据库里创建一条「待确认」记录（AgentPendingAction）。

  1. 用户或 Agent 调用发布相关工具 → 生成待确认记录。
  2. 前端弹出「确认发布《标题》？」→ 用户点确定。
  3. 前端调 POST .../confirm → 后端才真正调微信发布接口。

排期（schedule_content）同理：先提议，人确认后才写入排期时间。

4. API 端点清单

基础路径 /api/v1/agent · 鉴权 Authorization: Bearer <token> · 创作主权限 content.create

怎么选接口？

  • 第一次进创作页 → POST /sessions 建会话，把返回的 id 存 localStorage。
  • 用户每发一句话 → POST /sessions/{id}/chat 或 /chat/stream（要打字机效果用 stream）。
  • 点「一键创作」前 → 可先 preflight 判断输入够不够；再 POST /workflows。
  • 工作流 paused 后 → POST /workflows/{id}/resume 带上选的方案序号。
  • 点发布 → 查 GET /ops/pending 或直接用返回的 action_id → confirm。

会话GET/sessions · /sessions/{id}列表 / 详情

AgentChatResponse.action 与前端 UI 映射

每次 chat 或 chat/stream 结束后，看响应里的 action 字段决定 UI 怎么画——这是前后端最重要的「契约」。

action含义前端处理（Create.vue）
clarify信息不足 / 边界展示 clarify_question 文本气泡
proposals选题方案方案卡片列表，用户点选 index
generate正文已生成展示 content.body + 编辑/发布入口
chat闲聊回复普通助手文本
示例：用户说「你好」→ clarify 或 chat；说「小红书，少儿编程招生」→ 通常 proposals；说「写第 2 个」并带 selected_proposal_index: 1 → generate。

5. 前端调用示例

封装位置：Web apps/web/src/api/client.js · H5 apps/mp/src/utils/api.js · 业务页 Create.vue

推荐接入顺序（Web 创作页）：

  1. createSession — 拿到 sessionId，建议写入 localStorage，下次打开可复用。
  2. （可选）preflight — 一键创作前检查用户输入是否够具体。
  3. chatStream 或 chat — 发用户消息；根据返回 action 更新消息列表。
  4. 若 action==='proposals' — 渲染方案卡片；用户点击后带 selected_proposal_index 再 chat 一次。
  5. 若走 Workflow — createWorkflow → 等人选 → resumeWorkflow → 用 content_id 拉正文。
  6. 发布 — 必须走 Confirm API，不能假设 chat 返回即已发布。

6. 三种编排模式

同一套 Agent 能力，有三种调度方式。产品默认用模式 A；B、C 用于特定场景。

模式入口流式适用场景
A 意图解析（默认）chat_service✅ stream创作页主路径；结构清晰、易控额度
B ReActorchestrator❌复杂多步推理；LLM 自主选工具（≤8 步）
C Workflowworkflow_manager—一键创作；步骤可审计、可暂停

意图解析链路： 用户消息 → parse_intent → proposals|generate|clarify|chat → content_generation_service

ReAct 输出 JSON： {"step":"tool_call","tool":"...","arguments":{}} 或 {"step":"done","action":"...","message":"..."}

怎么选？

  • 模式 A——创作页日常对话、要流式输出、要可控扣费 → 默认即可。
  • 模式 B——需要 AI 自己多步试（如先搜库再出方案再写稿），请求体加 mode: "react"；注意不支持 stream。
  • 模式 C——「一键创作」按钮、需要步骤可追溯、要在出方案和写稿之间暂停 → 用 Workflow API。

7. 多 Agent 角色（supervisor_service）

不是五个独立的大模型，而是同一套系统里的五个「岗位」：每个岗位只能调用自己白名单里的工具，由 Supervisor 在步骤之间交接（handoff）。

类比：Creator = 文案；Compliance = 法务审稿；Ops = 运营发版（但发之前要人签字）；Seo = 标题优化；Supervisor = 项目经理派活。

Code名称职责工具白名单（节选）
supervisorSupervisor路由与 handoff—
creatorCreator检索、策划、撰写search_knowledge, generate_*, revise_content
complianceCompliance合规审查check_compliance
opsOps发布就绪 + Confirmreview_for_publish, publish_content, schedule_content
seoSeo标题标签优化optimize_metadata

合规 block → handoff 回 Creator 改稿；pass/warn → handoff 到 Ops 做发布就绪检查。

Workflow 跑完后，可在 GET /supervisor/workflows/{id}/handoffs 查看 Agent 之间交接记录，便于排查「卡在哪一步」。

8. Tool Registry（17 个）

工具 = 智能体可以执行的原子能力。ReAct 模式里大模型自己选工具；Workflow 模式里按 Pipeline 固定顺序调工具。所有调用都经 execute_tool，会检查当前用户角色有没有权限。

扣额度说明： 只有 generate_content（正文入库）在 llm_source=platform 时成功后会扣 1 次平台额度；出方案、预检、合规检查等不扣。

get_content / get_quota / get_wechat_settings / get_calendar否—辅助查询

创作链路常用工具顺序（Workflow）：

search_knowledge → analyze_pain_points → generate_proposals →（人选）→ generate_content → optimize_content → check_compliance → review_for_publish

9. Confirm 闸 API 示例

前端发布按钮的典型实现：先让用户看到待发布摘要，确认后再调 confirm。若用户取消，调 cancel，待确认记录作废，内容仍在草稿里。

状态字段：AgentPendingAction.status 为 pending / confirmed / cancelled。

// 查询待确认动作
const { data: pending } = await api.get('/api/v1/agent/ops/pending')

// 用户点击「确认发布」
await api.post(`/api/v1/agent/ops/actions/${actionId}/confirm`)

// 取消
await api.post(`/api/v1/agent/ops/actions/${actionId}/cancel`)

10. 当前方案优劣势

我们采用的是「混合编排」架构：不是单一 ReAct 或单一工作流，而是把意图解析（确定性）、ReAct（自主性）、Workflow（可审计流水线）、多 Agent 分工、Confirm 闸（人机协同）叠在一起。这在 To B 营销场景里偏务实，但也有工程复杂度。

✅ 优势（为什么这样设计）

  • 安全可落地——权限、额度、数据范围、发布确认全在 API 硬约束（BR-01），适合企业客户，优于「纯 Prompt 约束」。
  • 体验与成本可控——默认意图解析 + 流式；出方案不扣额度，只有正文入库扣 1 次，比全程 ReAct 更省 Token。
  • 人机协同到位——Workflow paused 等人选方案；Confirm 闸等人确认发布；符合合规与业务审核习惯。
  • 职责可解释——Creator / Compliance / Ops 分工 + Workflow 步骤落库，出问题能追溯「卡在哪一步」。
  • 知识与人格可运营——RAG + 人格库 P-001～P-009 + 长期记忆，内容风格可持续调优，非一次性 Prompt。
  • 扩展性好——Tool Registry + Pipeline 注册表；v1.6 销售经理、v1.7 商城创作可复用同一运行时。
  • 私有化友好——自研 FastAPI 栈，租户自有 LLM Key，不绑定单一云 Agent 平台。

⚠️ 劣势与局限（已知短板）

  • 编排路径偏多——chat / stream / react / workflow / preflight 五套入口，逻辑有重叠，维护成本高。
  • 意图与 ReAct 重复——「该出方案还是写正文」既在意图解析里判一次，ReAct 里又可能再判，行为一致性要靠测试兜底。
  • ReAct 无流式——多步 Tool 场景用户体验不如创作页 SSE，且 8 步上限可能不够复杂任务。
  • Pipeline 写死在代码——改步骤要发版；不如 LangGraph / YAML 配置灵活。
  • Supervisor 较「轻」——handoff 主要是步骤级 agent_code 标记，非真正多 Agent 并行对话或协商。
  • 可观测性不足——缺统一 Trace（每步 LLM/Tool 耗时、Token、失败率），排障靠日志和 DB 步骤表。
  • 记忆召回偏简单——keyword/hybrid，无专门记忆压缩与重要性打分；长会话仍可能丢上下文。
  • Eval 体系弱——有 verify 脚本，但缺 Prompt/工具选择的自动化回归与线上效果监控。

适用 vs 不适用

场景是否适合当前架构说明
营销内容创作（公众号/小红书/抖音）非常适合主战场，创作页 + Workflow 已验证
需人工确认的高风险写操作（发布/排期/对外报价）非常适合Confirm 闸专为此设计
销售管理多域推理（CRM + 报表 + 邮件）部分适合需 v1.6 扩展工具与子 Agent，MVP 用 Supervisor + 工具集
完全自主、7×24 无人值守 Agent不适合当前强依赖人机确认，非自治 Agent
超复杂开放域推理（上百步、多外部系统）不适合8 步 ReAct + 固定 Pipeline 覆盖有限

11. 业界智能体架构对比

智能体架构近几年快速演进。下表用同一维度对比常见范式与我们当前方案，便于判断「该学什么、该坚持什么」。

11.1 六种主流范式（由简到繁）

范式代表产品/框架核心机制优点缺点
① 单轮 RAG 聊天 早期客服机器人、文档问答 检索片段 → 拼 Prompt → 一次生成 简单、便宜、延迟低 无工具、无多步、难做业务闭环
② ReAct / Tool Calling OpenAI Assistants、早期 AutoGPT LLM 循环：思考 → 调工具 → 观察 → 再思考 灵活、开放域任务强 难控费、难审计、易幻觉乱调工具
③ 意图路由 + 固定链路 多数 To B Copilot、我们的 chat_service 先分类意图 → 走固定业务函数 稳定、可测、成本可控 新意图要改代码；灵活性低于 ReAct
④ 工作流 / 状态机 Temporal、n8n、我们的 workflow_manager 预定义步骤 + 暂停/恢复 + 持久化状态 可审计、可人机协同、适合长流程 编排变更需设计 Pipeline；不够「聪明」
⑤ 多 Agent Supervisor CrewAI、MetaGPT、我们 + v1.6 销售经理 主管拆任务 → 专家 Agent 分工 → 汇总 职责清晰、可扩展专业域 调度复杂、延迟高、上下文传递难
⑥ 图编排引擎 LangGraph、Microsoft AutoGen、AWS Bedrock Agents 有向图节点（LLM/Tool/Human）+ 条件边 + 检查点 统一表达 ReAct+Workflow+Human-in-loop 学习曲线、基础设施要求高

横轴 = 可控性（权限/审计/Confirm/可测）；纵轴 = 自主性（多步推理、自主选工具）。我们刻意偏右上方，但不过度自治。
