## 1. 业务闭环逐项评估

### 1.1 商家入驻闭环 —— ✅ 闭合（设计内）
- 链路：`智营注册(tenant)` → `A20/P02-A 提交` → `OCR 预填` → `P03 人审` → `shop_merchant_accounts` → `A17 开店` → `A15 支付进件`（§2.1.0 / §2.1.1 / §8.7.3；§2.4.4 为入驻状态变更，非支付进件）。
- 证据：双通道、三类主体字段显隐、OCR 不自动通过、驳回可重提、名称三态约定（legal/display/store）清晰。
- 缺口：无（属 Phase 1 目标）。

### 1.2 套餐 / 订阅闭环 —— ⚠️ 逻辑闭合 / 依赖人工
- 链路：`P10 配置` → `P11 人工开通` → `A18 只读` → `F8 合并` → `F9 用量计数` → `P02-B-R 续费申请` → `P11-A 处理`（§2.3 / §2.4 / F8 / F9）。
- 证据：aggregate_mode（any/max/sum）、stack/replace、到期回落免费版、管家无 P11 写权转交续费申请，逻辑自洽。
- **缺口（设计内，但需明示）**：
  - 商家自助购套餐、剩余天数折算、自助换档 **全部 Phase 2**（§1.1 🚫 列表）。Phase 1 走"线下对公 → P11 人工"——这是**业务闭环的人肉补丁**，验收不阻塞，但文档应明示"资金流不在线闭环"。
  - 续费付费流程（§2.4.3）写明"对公转账在系统外"，即**钱与系统的勾稽靠人工备注**，无自动对账。

### 1.3 商品上架合规闭环 —— ✅ 闭合
- 链路：`A02/A03 建草稿` → `F6 上架闸(pending_review)` → `P09 人审 approved` → `on_sale`；拒驳回草稿（§四 状态机 / F6）。
- 证据：draft 不可直 on_sale、机审可直驳、Mx 首单禁跳人审、驳回原因留痕（P1-21）。
- 缺口：~~机审规则（`compliance_flags` 敏感词/类目）仅提"写 compliance_flags"，**具体规则引擎/词库来源未定义**~~ → 已补 [F6 §机审规则](./03-数据流.html#f6-auto-rules) · PRD [§四 #f6-auto-rules](./PRD-内容获客商城-phase1.md#f6-auto-rules)；Phase 1 允许 `stub` 全 flag。

### 1.4 私域交易闭环（小程序）—— ✅ 完整闭合
- 链路：`M04 下单(pending_payment)` → `微信支付` → `F1 回调开权(entitlements.active + enrollment)` → `M06–M10 履约` → `M12-A 退款` → `F2 关权(revoked)`（§8.9 / F1 / F2）。
- 证据：幂等键（client_token / notify_id / order_item_id）、重复回调只开 1 次权益、退款后播放/下载/核销即 403，全链路自洽。
- 缺口：无（M3 硬验收项）。

### 1.5 公域 Mx 闭环（抖店挂载→履约→退款）—— ⚠️ 90% 闭合，退款事件留白
- 链路：`A14 映射` → `F7 挂载闸(mapped+external_audit)` → `公域下单` → `F3 领权① / F3b 内付②` → `领权短信/绑定` → `履约` → `退款 → F2`（§3.5 / F3 / F3b / F7）。
- **证据充足处**：挂载闸前置校验、幂等 external_order_no、拒单三类原因、领权单次使用、Mx 验收 8 步用例清晰。
- **缺口（真·数据闭环断点，见 §2 详述）**：
  - **链路①退款事件未细化**：`/integrations/doudian/webhook` 在 §8.11 被标注"抖店订单/**退款**"，但处理步骤 1–7 仅覆盖 `order.pay_success`（建单+开权+领权短信）；**refund 事件如何解析 → 触发 F2 关权未写**。F2 流程图本身只画了"微信退款"路径。链路①的退款来自抖店而非微信，若按文档字面实现，链路①退款将**无法关权**，Mx 第 7 步用例会失败。
  - 链路②（dy-knowledge）退款同理未在 webhook 处理中展开。

### 1.6 核销 / 开票闭环 —— ✅ 闭合
- 核销：`A08 查码` → `F4 扣次` → `consumed`（§8.10 / F4）。已购履约不受 merchant 暂停影响，规则明确。
- 开票：`M13/A13 提交` → `issued/rejected`（F5）。缺口：**冲红仅标 `needs_red_flush`（Phase 2）**——已开票退款的"红冲"是开放边，F2 仅置标记不自动冲，需人工 Phase 2 补。

### 1.7 清结算闭环（平台→商家）—— ✅ 数据层已闭合（打款仍人工）
- 链路（页面层）：`订单/退款` → `F10 出批` → `P05 结算批次(pending)` → `P05-B 确认打款` / `P05-C 重试`（§8.14.3 / 06-平台端UI P05）。
- **2026-08-12 现状**：
  - 04 已建模 [`shop_settlement_batches` / `shop_settlement_items`](./04-数据模型.html#settle)。
  - 03 已有 **[F10](./03-数据流.html#f10)**（T+7 入池 · 周关账 · 负额结转）。
  - 退款冲正：F10 写入 `refund_reversal`；P05 列表/详情展示。
- **仍开放（设计内）**：Phase 1 打款为财务人工确认，非自动打款 API；与套餐费「线下对公」同属人肉补丁，验收不阻塞但须明示。
- ~~审计原文：11 条流无结算 flow / 04 无 settlement 表~~ → **已废止**（见文首勘误）。

## 4. 业务闭环边界总图（Phase 1 已知开放边）

```
[入驻]──✅──>[开店]──✅──>[上架闸]──✅──>[私域交易]──✅闭环
                                                    │
                                           [公域Mx]──⚠️ 退款事件(B1)
                                                    │
                                           [清结算]──✅ F10+表；打款人工(§1.7)
                                                    │
[套餐订阅]──⚠️ 线下对公+B2B人工(设计内留白)
[发票冲红]──⚠️ 仅标记,Phase2(I2)
[买家身份]──⚠️ 跨端未合并(I1)
```

**判定**（2026-08-12）：Phase 1「交易闭环」在私域与公域挂载/履约维度达成度很高；**清结算数据层已闭合**（F10 + settlement 表），打款仍为财务人工。仍存的真断点主要是 **公域退款回写 F2（B1）** 与 **买家跨端身份（I1）**。建议在 PRD §一或 §五 增加「Phase 1 闭环边界声明」，把 B1/I1/I2 等显式列为已知开放边，便于验收对齐。
