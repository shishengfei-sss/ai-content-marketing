## 2. 失败项根因剖析（共 11 个：R1×3 + R2×1 + R3×1 + R7×6，全部为测试侧/环境侧，**无产品回归**）

> 关键结论：**本轮发现的 11 个失败均不是产品缺陷，而是测试脚本/环境的健壮性问题**。这与"代码 QC（2026-08-15 上午）"结论一致——应用核心逻辑达标，问题在测试资产自身，应修的是测试脚本而非应用代码。R7 的 6 个失败已通过**隔离复现实证非产品**（见 §2.6）。

### 2.1 R1 · VP04-1 列表含种子类目（cat.vocational）
- 现象：`GET /admin/shop/categories?page_size=50` 返回 `total=74`，断言 `any(code=="cat.vocational")`。
- 根因：**分页不健壮**。种子类目 `cat.vocational` 真实存在（实测在第 2 页，连同 `.001`~`.015`、`.sales` 共 17 条），但 R1 跑前已累计 74 个类目（含脚本自建），`page_size=50` 只取第 1 页，种子类目被挤到第 2 页 → 断言误判失败。
- 定性：**测试分页缺陷**，非产品问题。

### 2.2 R1 · VP04E-3 子类目继承父 code 预览
- 现象：同一 `cat.vocational` 查不到 → `parent=None` → 断言 `False`（"no cat.vocational"）。
- 根因：与 2.1 **同源**（同一个 page_size=50 查询只查第 1 页）。
- 定性：**测试分页缺陷**，非产品问题（子类目 code 继承逻辑本身正确）。

### 2.3 R1 · VP02B-OCR 材料含识别快照
- 现象：`GET /admin/shop/merchants/{tid}` 的 `onboarding_materials.ocr_results` 为空（`ocr=0`）。
- 根因：**测试自种数据未命中目标申请单**。`merchant_service._build_onboarding_materials` 已正确把 `onboarding.ocr_results` 经脱敏序列化进响应（已实测：库内 16 个入驻申请带 `ocr_results`，接口回传字段 `ocr_results` 存在且正常）。失败仅因该轮 `_raw_contact_and_seed_ocr()` 选中的租户无匹配入驻申请单可种 OCR。
- 定性：**测试数据态依赖**，OCR 序列化链路已验证正常，非产品缺陷。

### 2.4 R2 · test_tc_p02_l01_merchant_list_shell（商家列表页壳）
- 现象：`assert page.get_by_role("button", name="查询").count() >= 1` → `assert 0 >= 1`（表格渲染断言已通过，仅"查询"按钮按可访问名没匹配到）。
- 根因：**UI 选择器/可访问名脆弱**。同轮 `test_ui_shop_admin.py` 商家列表 **14/14 通过**，证明页面与表格本身正常；该用例对"查询"按钮的 accessible-name 匹配过严（文案/渲染差异）。
- 定性：**测试选择器缺陷**，非产品问题。

### 2.5 R3 · test_ui_shop_mp_order_checkout（小程序下单支付）
- 现象：`ERROR at setup` → `TargetClosedError: Target page, context or browser has been closed`。
- 根因：**Playwright 基础设施抖动**——用例 setup 阶段浏览器上下文被关闭（无头环境资源压力下常见），非应用逻辑错误。该文件同轮另 1 用例通过、1 跳过。
- 定性：**测试基础设施偶发抖动**，非产品问题（建议重跑或加 browser 重连）。

### 2.6 R7 · 6 个失败（CRM 回归 746 项里 6 fail，99.5%）

R7 跑出 6 个 `[FAIL]`，经逐一定位与**隔离复现**，全部为非产品问题：

| # | 失败标识 | 所在段 | 根因 | 性质 | 复现验证 |

| 5 | VUAT-13-3 `admin 全可见` | UAT-13 | **派生断言**：因 4 的线索未建成，admin 可见列表里不含该 lead_id | 派生（同源 VUAT-13-1） | 同上 |

**核心判定**：R7 不是"产品回归"，而是**测试套件在单一共享 DB 上跑 1107 项、共享测试用户（marketing/sales）的 territory/role 态被前置步骤改写的非幂等/顺序依赖问题**。两处核心能力——活动线索计数（`lead_count`）与销售建线索（含区域规则）——在隔离复现中均**正确 201/2**，证明产品逻辑无误。

**建议（修测试，不修应用）**：
1. V2a-5-2：测试应在读取 `lead_count` 前显式断言两条线索 POST 返回 201，并对"刚写入即读取"加短暂可见性等待/重试，消除 WAL 读取抖动。
2. UAT-13：每个 UAT 步骤开头用 `ensure_crm_test_users` + 显式重置 SALES_A 默认销售区域（保证幂等），或在 `lead_body` 调用处直接传 `territory_id`，避免依赖共享用户态。
3. 长跑套件建议：为共享测试用户建立"每个子 round 重置默认区域/角色"的 fixture，从根上消除 1100+ 测试的顺序依赖。

## 4. 结论与建议

- **产品侧**：核心交易链路（M3~M7）、安全/PII、Mock 集成、E2E、CRM 回归、Agent 回归、商城 M0 回归**全绿**，**无功能性/安全性产品回归**。代码 QC 同日结论成立。
- **测试资产侧（应修的是脚本，不是应用）**：
  1. 类目查询断言改为"翻页/全量取数"或按 `code` 精确查，消除 2.1/2.2 假失败。
  2. VP02B-OCR 的种数据逻辑需保证选中租户确有入驻申请单（或先建单再种 OCR）。
  3. R2 m0f_fe 的"查询"按钮断言改用稳定选择器（如 `data-testid` 或按钮文本模糊匹配）。
  4. R3 mp_order 增加浏览器上下文重连/重试，消除 TargetClosedError 偶发。
  5. **R7 V2a-5-2**：读取 `lead_count` 前显式断言线索 POST=201 并加可见性重试，消除 WAL 读取抖动。
  6. **R7 UAT-13**：每个 UAT 步骤重置共享用户默认销售区域（幂等）或 `lead_body` 直接传 `territory_id`；长跑套件为共享用户建"每子 round 重置"fixture，消顺序依赖。
- **开箱签收**：R2/R3 为 UI 轮，仍建议按总册要求由产品本人走一遍三端冒烟（D3/D5/SMOKE）后正式签收开箱。
