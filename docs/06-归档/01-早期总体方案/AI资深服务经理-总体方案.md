# AI 资深服务经理 · 总体方案与实施规划

> 文档版本：v1.0-plan｜创建：2026-07-24｜关联系统：智营获客（v0.3.3 MVP + v0.4 Agent + v0.6 顾问 + v0.7–v1.5 CRM + 营销/线索/CPQ 三库 + v1.6 AI 销售经理 + v1.7 AI 营销经理）
>
> 一句话定位：**AI 资深服务经理 = 服务经理 / 客户成功经理的数字分身 / 客户全生命周期的"留存续航中枢"**。它不只是一个"智能客服机器人"，而是一个能替服务经理"定体验策略、管工单、做客服、保续费、看健康、带团队、把口碑反哺营销与销售"的 Supervisor 智能体。底层复用现有 Agent 框架，外层编排 CRM + 服务库 + 三库能力。

---

## 〇、与现有系统的关系（先说结论，避免重复造轮子）

本项目已有资产足以支撑"AI 服务经理"，**无须从零搭建**——v0.4 的 Agent 骨架、v1.6 的销售经理、v1.7 的营销经理已经把营销+销售"双中枢"跑通，服务经理是**并列的第三个 Supervisor**，直接上车同一套底座：

| 已有能力 | 位置 | 本方案中怎么用 |
|---|---|---|
| 多 Agent Supervisor 调度 | v0.4 Agent C5 | **直接作为"服务经理大脑"的编排骨架** |
| 子 Agent 注册表机制 | v1.6 FR-SALES-MGR-07 | 新增服务子 Agent 仅登记，不改调度核心 |
| ReAct 工具调用 / 长期记忆 L0–L4 | v0.4 Agent B/LM | 子 Agent 工具执行与跨会话记忆 |
| 工作流 + Compliance + Confirm 闸 | v0.4 Agent C1–C3 | **AI 不能擅自回复客户/关单/补偿/改 SLA**（沿用 BR-01） |
| 混合 RAG（pgvector + 重排） | v0.4 Agent C4 | 知识库/工单库/案例库检索的事实来源与溯源 |
| 营销创作顾问 | v0.6 Advisor | 直接复用为"服务官"的内容产出能力 |
| CRM 核心（线索/客户/商机/合同/回款） | v0.7–v1.5 | "服务官/客户健康官"的客户与交易数据底座 |
| 经营报表与预警 | v1.2 CRM 运营报表 | "服务官"的体验监控数据底 |
| 人格库 | 人格库设计手册 | 塑造"服务经理人格" + 对客/对客服沟通风格 |
| AI 营销经理（v1.7） | AI资深营销经理-总体方案 | **并列第一 Supervisor**，经"口碑/转介绍 SLA"协同 |
| AI 销售经理（v1.6） | AI资深销售经理-总体方案 | **并列第二 Supervisor**，经"成交移交 / 增购回流 SLA"协同 |

**结论**：本方案 = 服务经理版 Supervisor（服务人格 + 调度）+ 3 个服务核心子 Agent（服务官 / 客户健康官 / 知识官）+ 服务专属库/知识库 + 复用三库与 Confirm 闸。增量集中在"服务职责域拆解、服务专属库、职能提示词、三中枢闭环"，基建全部复用。

> **三中枢架构判断（本方案的核心增量）**：AI 营销经理、AI 销售经理、AI 服务经理是**三个并列的 Supervisor，共享同一套底座**（框架/人格库/三库/Confirm 闸/CRM 适配器），但职责域与数据侧重不同，通过**三条 SLA 协同线**串成客户全生命周期闭环：
> - **营销 → 销售**：MQL → 培育 → 移交 SQL（已有）。
> - **销售 → 服务**：成交/签约 → 客户交接 SLA → 服务接管 Onboarding → 续费/增购。
> - **服务 → 销售**：健康客户增购/升级信号 → 回流商机 SLA → 销售跟进。
> - **服务 → 营销**：满意客户口碑/UGC/转介绍 → 线索 SLA → 营销获客；缺陷/体验问题 → 产品反馈闭环。
> 不做成一个大杂烩，避免意图路由混乱与权限边界模糊——这正是与市面上"智能客服单点工具"最大的差异。

## 一、界定范围：资深服务经理到底做什么（职责全景）

先把"做服务经理所有工作"拆成 **10 大职责域、约 30 项具体工作**。这是产品规格，也是三大核心子 Agent（服务官 / 客户健康官 / 知识官）的职责归属依据。

| # | 职责域 | 具体工作项 | 对应子 Agent |
|---|---|---|---|
| 1 | **服务战略与体验管理** | 服务/客户成功定位；体验战略与 CX 指标（CSAT/NPS/CES）；SLA 体系设计；服务目标拆解 | 服务官 |
| 2 | **工单与服务请求** | 工单受理/分类/分配；优先级与 SLA 计时；升级/转派；关单质检 | 服务官 |
| 3 | **客户支持（咨询/故障/投诉）** | 售前售后咨询；技术故障诊断；投诉处理；紧急事件/危机响应 | 服务官 |
| 4 | **客户成功与留存** | Onboarding；客户健康度评分；续费管理；增购/升级；流失预警与干预 | 客户健康官 |
| 5 | **知识库与自助服务** | FAQ / 知识文章；自助问答；社区与文档；知识治理 | 知识官 |
| 6 | **服务质量与体验监控** | CSAT/NPS/CES 分析；情感分析；质检（QA）；首解率/时效看板 | 服务官 |
| 7 | **续费 / 增购 / 复购** | 续费提醒与推进；增购机会识别；客户升级路径；复购激励 | 客户健康官 |
| 8 | **服务团队管理** | 排班与负载；客服培训陪练；质检辅导；绩效与知识沉淀 | 服务官 |
| 9 | **跨部门协同闭环** | 与销售（交接/商机）、产品（缺陷反馈）、营销（口碑/转介绍）协同；周会/经营会 | 服务官 |
| 10 | **内容产出（对内外）** | 对客公告/SLA 说明/FAQ 话术；给老板的服务经营分析报告；给团队的话术/手册 | 服务官 |

> 设计判据（沿用前两份方案）：**凡是"确定性、可审计"的事（SLA 规则、分配规则、审批流、关单质检）用规则引擎/工作流打底；凡是"需要判断、生成、解释"的事（故障诊断、续费策略、投诉处置、复盘）交给 AI 做"建议"，关键动作经 Confirm 闸由人确认。**

## 二、产品形态与用户场景

### 2.1 三类使用者

| 角色 | 怎么用 AI 服务经理 | 典型场景 |
|---|---|---|
| **客户成功总监 / 老板** | 看全局、要续费判断、要体验健康度 | "今年续约率能达标吗？""哪些客户在流失边缘？""NPS 为什么跌了？" |
| **服务经理 / 客户成功经理** | 把日常管理甩给 AI | "把这批新工单按规则分给团队""帮我写这周的客户健康复盘和预警""这个投诉怎么处置、话术给我" |
| **一线客服 / 服务顾问** | 被 AI 辅助、被提醒、被辅导 | "这个故障怎么排查？""帮我起草给 X 客户的回复""这个客户下月到期，怎么谈续费？" |

### 2.2 入口与交互范式（复用三端）

- **Web 工作台**：经理视角总控台（健康看板 + 工单队列 + 对话）
- **H5 移动端**：一线随身助理（工单提醒、回复话术、客户健康速览）
- **IM 嵌入（企微/飞书，后续）**：主动推送 SLA 超时、流失预警、续费节点、舆情异动
- **交互范式 = 对话式为主 + 主动推送为辅**：AI 不只是"你问它答"，还会在 SLA 超时、客户健康骤降、续费临期、NPS 异动、重大投诉时主动报警。

**关键设计**：服务经理 Supervisor 不直接干活，它"理解意图 → 拆解任务 → 派给子 Agent → 汇总并解释 → 关键动作走 Confirm 闸"。新增服务子 Agent 全部走 v1.6 注册表机制（FR-SALES-MGR-07），**不改动调度核心**。所有引用带溯源（防幻觉）。

## 四、数据地基：服务专属库（决定 AI 能不能"做对事"）

服务经理的能力上限 = 数据 + 知识的质量。CRM 核心（客户/合同/回款）已有；但服务经理要"做全局决策"，还缺 5 个专属库。优先级：**先打通已建成的 CRM 与三库，再分批新建。**

| 库 | 状态 | 内容 | 来源/建设 |
|---|---|---|---|
| CRM 核心 + 三库 | ✅ 已有 | 客户/合同/回款 + 营销库/线索库/产品价库（话术/案例/产品知识） | 复用 v0.7–v1.5 + 三库 |
| 工单服务库 | 🆕 新建 | 工单全量（分类/优先级/SLA/处理过程/解决结果/升级） | 接入工单系统，结构化沉淀 |
| 知识库（KB） | 🆕 新建 | FAQ、知识文章、排查手册、自助问答语料 | 人工+AI 抽取工单沉淀，进 RAG |
| 客户健康度库 | 🆕 新建 | 健康分、使用行为、活跃度、参与信号、流失分 | 对接 CRM/产品使用数据，评分模型 |
| 服务体验库 | 🆕 新建 | CSAT/NPS/CES、情感、投诉、舆情、质检结果 | 接入调研/工单/社媒（合规公开源） |
| 解决方案案例库 | 🆕 新建 | 典型故障排查、投诉处置话术、增购打法、赢单/续约案例 | 从工单库/成功实践结构化抽离 |

> **权限/密级沿用现有 RBAC + 行级过滤**：工单/客户数据已有 L1–L4 分级与 AI 账号限制（禁批量导出、密级硬过滤、全审计）。新建库沿用同一套。客户隐私数据（PII）额外加脱敏与最小权限。

## 五、关键设计原则（复用 + 服务延伸）

| 原则 | 做法 | 出处 |
|---|---|---|
| **规则打底，AI 增强** | SLA 计时、分配规则、审批流用确定性引擎；AI 只出"建议" | AI 报价调研 + v1.6/v1.7 |
| **Confirm 闸** | 对外回复客户（尤其承诺/赔偿性）、关单、改 SLA、退款/补偿，必须经人确认 | v0.4 BR-01 |
| **可解释 > 准确率** | 健康分、流失预警、续费建议都要给"为什么"，否则经理不信任 | v1.6 |
| **防幻觉** | 知识库/工单库/案例库检索结果作为唯一事实来源，强制溯源 | v0.4 C4 |
| **人格一致性 + 共情** | 稳定服务经理人格 P-SVC（专业/共情/可靠/边界）+ 对客镜像沟通（客服语气） | 人格库手册（服务延伸） |
| **主动而非被动** | SLA 超时、健康骤降、续费临期、NPS 异动、重大投诉主动推 | v1.2 提醒机制延伸 |
| **体验可控** | 对外话术可批量生成但带"品牌 TONE + 合规校验"，承诺性内容偏离则拦截建议 | 新增（服务特有） |

## 六、分阶段实施路线图

> 依赖链：CRM 核心（已有）是前提；Supervisor 骨架（复用 C5）是中枢；服务子 Agent 分批点亮；最后做自治闭环与自进化。可与营销/销售经理并行推进（共享底座，省大量重复）。

### Phase 0 · 服务数据地基（前提，约 2–3 周）

- **目标**：让 AI"看得见、看得对"服务全貌。
- **核心交付**：CRM 客户/合同/回款对服务视角对齐；工单服务库表结构与采集管线（轻量起步）；知识库（KB）初版与 RAG 接入；RBAC 行级过滤与 AI 账号权限就位；PII 脱敏规则就位。
- **验收**：Agent 能经授权检索到工单历史/知识文章/客户合同并带溯源。
- **依赖**：CRM 核心（v0.7–v1.5）。

### Phase 1 · 服务经理人格 + Supervisor 调度骨架（MVP 中枢，约 1–2 周）

- **目标**：先有一个"会调度、有人格、守边界"的服务经理外壳。
- **核心交付**：
  - 在**人格库**新增"服务经理"稳定人格 `P-SVC`（专业/共情/可靠/边界），及"对客客服"镜像变体；
  - 基于 v0.4 **C5 Supervisor** 封装 `ServiceManagerSupervisor`：意图理解 → 任务拆解 → 派发占位子 Agent → 汇总解释；
  - Confirm 闸接入调度（对外回复/关单/补偿先 propose，人 confirm 才执行）；
  - 与营销/销售经理共享底座，预留「成交移交 / 增购回流 / 口碑转介绍」三条 SLA 协同接口。
- **验收**：对话能识别"分工单/写健康复盘/看 NPS/想续费策略"等意图并正确派发；危险动作被闸拦住。
- **依赖**：v0.4 C5 + 人格库 + v1.6 注册表。

### Phase 2 · 三大核心子 Agent（最快见效，约 3–4 周）

- **目标**：先点亮经理最高频、数据最齐的三块，对应统一方案的 3 个服务子 Agent。
- **核心交付**：
  - **服务官（ServiceAgent）**：工单分类/优先级/SLA 计时/按规则分配与升级建议（接规则引擎）；知识库检索 + 故障诊断建议 + 起草对客回复（带 TONE/合规校验），复用 v0.6 生成能力；CSAT/NPS 趋势、SLA 达成、首解率、情绪告警等体验监控；团队排班负载与内容产出。
  - **客户健康官（HealthAgent）**：客户健康度评分、流失预警与干预、续费推进、增购信号识别（与销售 SLA 协同）、Onboarding 节奏。
  - **知识官（KnowledgeAgent）**：知识库维护、FAQ 自动生成、自助问答语料治理、从工单反哺知识。
- **验收**：能回答"这周 SLA 达成率多少、哪类工单超时""这个故障怎么排查、回复话术给我""哪些客户在流失边缘、怎么救"；生成内容带溯源与 TONE 校验。
- **依赖**：Phase 0 + Phase 1。

### Phase 3 · 三大子 Agent 深化 + 覆盖全部 10 职责域（约 4–6 周）

- **目标**：在 3 大子 Agent 内补全 10 大职责域能力，形成完整服务经理职能。
- **核心交付**：
  - **服务官** 深化：服务战略与体验管理（CX 指标 / SLA 体系设计）、投诉处置与危机响应、跨部门协同（与销售交接/商机、产品缺陷反馈、营销口碑转介绍）、服务经营会材料自动生成；
  - **客户健康官** 深化：续费 / 增购 / 复购全链路、客户升级路径、复购激励、健康分归因；
  - **知识官** 深化：社区与文档治理、案例库结构化（从工单/成功实践抽离典型排查/话术/续约案例）。
- **验收**：端到端跑通"工单→分配→支持→关单质检→健康预警→续费/增购→回流销售→口碑反哺营销"全链路，关键节点有人确认。
- **依赖**：Phase 2。

### Phase 4 · 自治闭环（约 3–4 周）

- **目标**：从"你问它答"到"它主动管"。
- **核心交付**：事件驱动预警（SLA 超时/健康骤降/续费临期/NPS 异动/重大投诉主动推）；周期性自动产出（日报/周报/月服务经营会材料/知识库自动补位）；自动化工单分配与升级（基于负载与优先级）；自动续费提醒与流失干预建议。
- **验收**：模拟 SLA 超时/健康骤降能主动报警并给处置建议；周期报告按时自动生成。

### Phase 5 · 自进化（持续）

- **目标**：越用越像"资深"。
- **核心交付**：复盘自动沉淀进知识库（排查方案/话术/续约案例/坑）；检索与模型季度迭代；效果评估看板（首解率、CSAT、续约率、增购率、AI 建议采纳率）。
- **验收**：知识库月增长可量化；续约率/健康分归因准确率持续提升。

> 总工期估算（核心研发）：约 **4–5 个月**到达 Phase 3 完整职能；Phase 4–5 持续迭代。可与 AI 营销/销售经理并行推进（共享底座，省大量重复）。

## 七、推荐的 MVP 第一刀（先证明价值）

**建议 Phase 1 + Phase 2 合并为第一个可演示闭环**，范围刻意收窄：

- 服务经理人格 P-SVC + Supervisor 调度骨架（Phase 1）；
- **服务官 + 客户健康官 + 知识官（3 大核心子 Agent）**；
- 数据仅用**已建成的 CRM + 轻量工单库 + 初版知识库**。

**为什么选这刀**：CRM 已就绪（数据最齐）、价值最直观（降首解时长/提 SLA 达成/稳 CSAT）、风险最低（对外回复全走 Confirm 闸、写动作受限）、能最快给胜非一个"会当服务经理的 AI"演示。

**MVP 验收 demo**：打开工作台，"这周 SLA 达成率多少、哪类工单在超时" → 服务官给可解释看板；"这个故障怎么排查、给我一段对客户的话术" → 服务官生成带 TONE 校验的回复，提交前需人确认；"哪些客户在流失边缘、怎么救" → 客户健康官给健康分与干预建议；"新进 20 条工单按规则分给团队" → 服务官按优先级/SLA/负载分配并标注升级项。

## 八、创业视角：差异化与商业模式（给胜非的额外参考）

| 维度 | 判断 |
|---|---|
| **定位差异化** | 不做"智能客服机器人"（趋同于网易七鱼/智齿/腾讯企点），做"**能替经理做体验决策和全盘客户经营管理的 AI 服务经理**"——中枢编排而非单点功能。对标 Salesforce Service Cloud + Agentforce、Gainsight（客户成功），但更强调**私有化 + 行业服务知识护城河 + 与营销/销售三中枢闭环**。 |
| **护城河** | 服务/工单/健康度数据 + 行业服务知识（排查/话术/续约打法）+ 可解释 + 私有化部署。通用大模型没有你的行业服务历史与案例。 |
| **竞品站位** | 国际：Salesforce Service Cloud/Agentforce、Zendesk、Gainsight；国内：网易七鱼、智齿、腾讯企点、销售易服务云。我们缺口在"全职能服务主管 Agent + 与营销/销售/服务三中枢联动"这一层——别人多是单点客服或孤立 CSM。 |
| **三中枢协同卖点（独家）** | 营销获客 → 销售转化 → 服务留存续航 → 口碑反哺获客，一条数据链打通。客户成功数据直接喂给销售（增购商机）和营销（转介绍线索），这是单点服务工具做不到的**飞轮效应**。 |
| **商业模式** | 私有化项目制（中大型 B2B/制造业/ SaaS 大客户）+ SaaS 按席位/按调用量；"AI 服务经理"作为高阶套餐溢价点，与"AI 营销经理 + AI 销售经理"打包成 **"AI 经营三中枢"** 整体方案。 |
| **合规卖点** | Confirm 闸 + 审计 + 密级隔离 + PII 脱敏 + 品牌 TONE 校验，解决企业"不敢让 AI 擅自回复客户/关单/补偿"的顾虑——To B 落地刚需。 |

## 九、风险与待胜非拍板的事项

**主要风险**
- 服务数据割裂：工单/健康度/体验数据往往散落在工单系统、客服后台、产品埋点，需打通才有健康分与归因（先 Phase 0 治理，轻量起步）。
- 幻觉边界：对外回复/投诉处置/续费承诺必须可解释+溯源+人确认。
- 过度自动化：回复/关单/补偿等高风险动作必须 Confirm 闸，不能全自动。
- 隐私合规：客户 PII 在知识检索与生成中需脱敏与最小权限。
- 成本：多 Agent + RAG + 大模型调用，需按调用量核算。

**需要胜非决策（决定下一步怎么切）**
1. **三中枢边界**：同意"AI 营销 / 销售 / 服务 三个并列 Supervisor、共享底座、经三条 SLA 协同"的架构吗？还是先做"服务单中枢"再逐步并入？（影响是否同步改前两份方案为三中枢架构图）
2. **工单系统现状**：现有 CRM 是否含工单/售后模块可复用？还是要新建轻量工单库？（影响 Phase 0 范围与工期）
3. **第一刀范围**：是否同意按第七节 MVP（服务官+客户健康官+知识官）先做出可演示闭环？
4. **行业聚焦**：先打透 B2B 制造业（已有 CPQ/客户积累可作协同），还是 SaaS/消费服务？—— 影响知识库与话术建设。
5. **人工介入深度**：Confirm 闸边界设多严（建议：一切对外回复/关单/补偿/改 SLA 都确认，内部分析/草稿/知识检索可自动）。
